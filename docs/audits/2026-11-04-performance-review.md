# 性能检查结果（2026-11-04）

## 范围与结论

检查 Vue 3 / Vite 前端、Tauri Rust 命令、日报历史扫描、DevDock 轮询和 Diff 渲染；执行生产构建与 Node 合成微基准。未启动浏览器、未运行自动化视觉验证、未读取用户真实会话数据，也未修改业务代码。原有 `src-tauri/Cargo.toml` 修改保持原样。

存在值得优化的点。优先处理日报选择查询的平方级计算、启动依赖，以及历史文件重复扫描；其次处理缓存页面轮询和大型 Diff。下列优先级表示优化顺序，不表示已经测得线上故障。

## 构建与测量

- `npm run build` 成功，包含 TypeScript 检查；Vite 构建阶段报告 18.42 秒、转换 4818 个模块。构建时间是本机单次结果。
- 主入口 JS：2646.86 kB，gzip 804.47 kB；入口 CSS：332.48 kB，gzip 46.09 kB。
- MarkdownDocumentViewer JS：652.75 kB，gzip 157.42 kB。其他 Mermaid 图表分块按需加载，不能把 dist 所有文件相加当成首屏下载量。
- `highlight.js` 默认导入在当前安装版本中注册了 193 种语言。
- Tauri 从本地提供资源，gzip 体积仅作比较；实际启动还取决于解压、JS 解析和执行、IPC 和系统环境，不能由包体直接换算启动耗时。

Node 合成微基准（单次样本，非 WebView 实机结果）：

| 会话 ID 数量 | filter + Array.includes | 构建 Set + filter + Set.has |

| 1000 | 12.31 ms | 0.12 ms |
| 5000 | 254.08 ms | 0.98 ms |
| 10000 | 1250.47 ms | 1.79 ms |

## 1. 高优先级：日报选择状态存在平方级计算

证据：

- `src/views/codex-report/CodexReportView.vue:195` 起，includedSessions、excludedSessions、listSessions 在遍历列表时使用 `includedIds.value.includes(sessionSelectionKey(session))`。
- `src/views/codex-report/components/CodexSessionList.vue:79` 起，完整 v-for 渲染所有会话，每个条目又多次执行同类 includes。

当可见会话数和选中数都随数据增长时，成员判断为 O(N×M)，全选时接近 O(N²)。日常少量会话影响有限，较长日期范围和集中选择更容易放大开销。上面的纯算法样本已显示这一趋势。

建议：保留数组作为选择状态，对它建立 computed Set；所有成员判断统一走 Set.has。会话量仍很大时，再分页或虚拟化列表。

验收：使用 1000 / 5000 / 10000 条固定会话，比较筛选、全选、切换纳入状态的耗时及结果一致性。

## 2. 高优先级：启动同步依赖过重

证据：

- `src/router/index.ts:3`–`6` 同步导入 Git、DevDock、日报和设置页面。
- `src/App.vue:20` 只为获取启动 Markdown 路径，导入整个 markdown-service；后者 `src/services/markdown/markdown-service.ts:6` 同步导入完整 highlight.js，并同步导入 Marked、DOMPurify。
- `src/components/skills/TopbarSkillsPill.vue:35` 和 `src/components/quota/TopbarQuotaPill.vue:39` 同步导入功能弹窗。
- `src/main.ts:25` 在 app.mount 之前等待 AI 设置初始化。

结果：进入默认 DevDock 或独立窗口时，也需要处理不立即使用的业务与 Markdown 依赖。生产包已经测得入口 JS 约 2.65 MB；具体各依赖贡献比例未运行模块归因工具，不能给出精确拆分。

建议：路由改为按需导入；拆出轻量的 Markdown IPC 服务；渲染器与高亮按需加载，按产品支持范围注册语言，未知语言保留纯文本回退；弹窗首次打开时加载。AI 设置是否改为挂载后加载，应先明确依赖它的功能就绪状态。

验收：比较优化前后的入口 JS 及各路由分块；实机测量冷启动、主窗口和独立 Markdown / Diff 窗口的可交互时间，并验证首次进入功能的等待状态。

## 3. 高优先级：日报查询重复遍历、解析全历史

证据：

- `src-tauri/src/commands/codex_report.rs:414` 起，每次查询都收集历史目录全部 JSONL / ZST 文件并调用解析器；Codex 解析器在逐行读取后再判断消息日期（约 549 行起）。
- 项目列表加载同样扫描历史，Claude 项目聚合调用完整会话解析（约 283 行起）。
- `src/views/codex-report/CodexReportView.vue:276` 同时启动项目列表与会话加载；日期或来源变化又触发查询。
- 前端 loadSequence 可以丢弃旧响应，但不会取消已提交的后端扫描任务。

结果：即使只查询一天，读取量仍可能随全部历史体积增长；首次打开存在重复扫描，快速切换筛选可能让多个扫描并存。已有 spawn_blocking 和最多 8 个解析线程有助于并行，但不会消除重复 I/O。未以真实历史库测量耗时。

建议：按文件维护增量解析缓存或 SQLite 索引，复用项目汇总与会话数据；对变化文件更新索引，查询使用消息时间；补充请求合并、防抖或取消。不要仅按目录日期或文件 mtime 排除历史文件：现有代码明确兼容归档、压缩、迁移和恢复会话，简单裁剪会漏数据。mtime / size 可用于缓存失效判断，并配合新增、删除、截断等情况处理。

验收：固定历史样本测试首次、重复、单文件追加、归档恢复、文件删除后的查询耗时与结果完整性。

## 4. 中优先级：KeepAlive 页面停用后仍可能轮询

证据：

- `src/layouts/MainLayout.vue:94` 用 KeepAlive 缓存业务页面。
- `src/views/markdown-preview/MarkdownPreviewView.vue:383` 起每 3 秒获取文件元数据，仅在 onUnmounted 清理；没有 onDeactivated 和窗口隐藏处理。
- `src/views/devdock/DevDockView.vue:255` 停用时只停止进程轮询，没有停止日志轮询；日志打开状态下每秒继续获取快照。
- DevDock 的 visibilitychange 监听器直到卸载才移除；窗口重新可见时，无论 DevDock 是否当前页面都会重新启动进程轮询（约 691 行起）。

结果：打开 Markdown 后切换模块，元数据查询仍会继续；DevDock 离开后仍可能产生日志请求，或在窗口重新可见时恢复后台进程请求。日志后端有 500 条环形缓冲上限，不属于无限日志增长问题，但每次获取仍克隆整个缓冲。

建议：用页面 active 与窗口 visible 两个条件统一管理任务，在停用时停止、激活时恢复；日志获取引入增量游标或版本号，无变化时不替换整个数组；异步轮询加入 in-flight 控制，避免慢请求重叠。

验收：打开日志与 Markdown，切到其他模块，隐藏再恢复窗口；确认非当前模块没有继续请求，回到模块能恢复并显示最新内容。

## 5. 中优先级：大 Diff 全量渲染，滚动还扫描所有行

证据：

- `src/views/git-assistant/components/GitDiffViewer.vue:93` 起在前端调用 diff2html.html，一次生成完整 HTML 后注入。
- `src/views/git-diff/UnifiedDiffViewer.vue:30` 起全量渲染 hunk 与行；每个 scroll 直接调用 syncViewport。
- syncViewport（约 126 行起）每次查询所有行，并调用 getBoundingClientRect 查找可见范围。这里的 viewport 用于定位条，不是行虚拟化。

Node 合成测试：5000 行纯新增生成约 1.76 MB HTML，耗时 29.08 ms；10000 行约 3.52 MB，耗时 38.58 ms。测试不包含 DOM 插入、布局和滚动，因此不能将这些数字当成页面打开耗时。当前证据也不足以认定 matching: lines 本身是主要瓶颈。

建议：大 Diff 使用虚拟列表、按 hunk 分块，或先折叠上下文；定位条按行高和 scrollTop 计算范围，必要时用预计算偏移；滚动回调按动画帧合并，避免每次扫描全部 DOM。小 Diff 保留现有简单路径。

验收：固定 1000 / 10000 / 50000 行样本，观察首次显示、滚动帧时间、DOM 数量，以及定位条精度。需要用户手动验证或另行授权浏览器验证。

## 6. 中优先级：停止进程的同步等待占用异步执行线程

证据：

- `src-tauri/src/commands/project_process.rs:134` 起 async 命令直接调用同步停止逻辑；批量停止、重启也进入同步路径。
- `src-tauri/src/commands/project_process/process_runtime.rs:593` 起 stop_process 执行进程终止，并最多循环 20 次，每次 thread::sleep 100 ms。

结果：进程迟迟不退出时，一次调用可在该循环内累计阻塞约 2 秒，另有系统命令耗时；同时操作多个进程时会增加运行时线程压力。尚未测量正常与异常停止场景。

建议：将整段同步进程控制放入 spawn_blocking，或改为异步子进程与 tokio::time::sleep；保留超时与状态确认，避免仅取消等待导致错误报告停止成功。

验收：正常退出与延迟退出子进程场景下，停止结果正确，其他 IPC 请求仍可及时返回。

## 建议顺序与限制

先做成员判断 Set 化、启动依赖拆分、轮询生命周期修正；这些改动范围相对可控。再做历史增量索引和大 Diff 渲染，以固定样本保证兼容性。进程阻塞隔离可单独修复。

现有正向措施包括：图标生成脚本只打包使用的图标（141 个 Solar、1 个 MDI），技能目录具备 SQLite FTS 检索，日报解析已有后台线程与并行控制，日志有 500 条上限，DevDock 普通停用流程已有进程轮询清理。无需重复建设这些机制。

本次没有浏览器 / Tauri 实机性能剖析、FPS、启动时间或内存曲线，也没有执行 Rust 编译和整个测试套件；结论以静态代码、生产构建和纯算法样本为依据。业务代码没有改动，后续实施时再运行与改动直接相关的测试。

### 实际限制和手动验收

缓存只在当前进程内生效，重启后的首次读取仍需扫描文件，超出缓存容量的历史仍走流式读取。构建保留 Vite 大分块提示，Mermaid 及图表库按需加载。没有执行浏览器自动化、截图或 Tauri 实机 UI 验证，也未测量真实冷启动、FPS 或内存曲线。

请手动检查：

1. 日报取消全选、反选、重开应用后的零选择，以及筛选/日期变化后生成内容一致；损坏来源应出现不完整提示，正常来源仍可用。
2. Skills/额度弹窗首次打开就有正常加载行为；关闭再打开后状态正确。
3. 打开 Markdown 和 DevDock 日志，切换模块、隐藏再恢复窗口；回到原模块后更新正常，日志搜索与滚动正常。
4. 打开大 Diff，滚动到末尾、拖动定位条、调整窗口宽高；长行横向滚动、行号及修改色块正确。
5. 正常与延迟退出的开发进程执行停止、重启、退出应用时，状态正确且其他操作仍响应。
