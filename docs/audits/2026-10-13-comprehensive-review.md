# Halowake 全面评审：主工作流、Skills 中心与复杂度收敛

评审日期：2026-10-13。评审对象是当前工作区，包含未提交和未跟踪的源码，不仅是 HEAD。没有修改业务源码。

## 结论

项目具备可以继续迭代的基础；Skills 中心目前不适合继续增加能力或扩大其可靠性承诺，应先完成一次围绕身份、安装结果和数据一致性的收敛。

用户感觉“失控”有代码依据：一个模块同时承担本地盘点、远端目录、推荐评分、自然语言搜索、分类收藏、来源说明、单技能/合集/流水线安装、多工具部署、升级和历史记录。这些能力增长得比统一身份模型、失败语义和回归测试快。结果是正常路径越来越丰富，边界路径却互相矛盾。

不建议全盘推倒重做。Git 提交保护、进程管理、SQLite 事务、安装锁、崩溃恢复、主题令牌等已有投入值得保留。应暂停 Skills 新功能，先修复数据保护与“虚假成功”，再收敛搜索和界面。

## 评审方式与证据边界

- 深入追踪 Skills 的 Vue → Pinia → IPC → Rust → 文件系统/SQLite 链路。
- 抽查 Git、DevDock、会话日报、额度、设置/存储、Markdown 和发布检查配置。
- 执行前端 lint、生产前端打包、Rust 库测试、搜索集成测试和 diff 空白检查。
- 在隔离的 Node 环境中运行当前前端源码片段：真实 Vue/Pinia/TypeScript，替换网络和安装 IPC，不启动浏览器、不安装真实技能。
- 搜索集成测试读取本机现有目录数据库的技能条目，生产评测使用独立临时数据库；原数据库以只读方式打开。
- 按用户 AGENTS.md，未启动或控制浏览器，未执行自动化视觉验证。可用性结论来自代码中的交互实现；实际布局、对比度、缩放和焦点行为仍需手动验证。
- 这是有重点的全项目工程评审，不是每个服务商接口和每个操作系统上的全面运行验收。

优先级：P1 为发布前应解决的数据保护/主流程问题；P2 为下一轮稳定性和维护性问题；P3 为可随后处理的改进。证据分别标注“执行复现”“静态确定”和“静态风险”。

## P1：先处理主流程和数据保护

### F01 合集子技能的身份去重会把第二个子技能当成第一个

**证据：静态确定。** `src/stores/skill-explore.ts:527` 附近对合集逐项安装，传入相同 `skillId: parent.id`、不同 `subSkillId` 和 `subPath`。后端 `src-tauri/src/commands/skills.rs:460` 的 2a 分支在 `catalog_id` 和仓库相同后，直接返回已有目录，没有比较子技能路径。

触发场景：合集含 A、B 两个子技能，A 已安装或刚安装完成。安装 B 时，其来源记录与 A 具有相同父级 catalog ID 和仓库，扫描命中 A。

影响：全局/指定 Agent 模式把 B 当作已存在并返回成功空路径；项目模式返回“已存在”。用户可能看到部分失败，或被告知整套已装好，而 B 实际不存在。

建议：把可安装单元标识与合集标识分开。子技能身份至少包含规范化仓库与 subPath；catalog ID 只能作为目录条目的关联，不能单独覆盖子路径。兼容旧目录的特殊分支也要校验真实来源。

验收：同一仓库、同一合集内连续安装 A/B，各自产生正确目录；再次安装只跳过相同子技能，不跳过同合集的其他成员。

### F02 未受管技能自动更新会覆盖本地文件，且来源由名称猜测

**证据：静态确定。** `src-tauri/src/commands/skills.rs:1805` 开始的非 Git、非受管更新分支通过 `resolve_unmanaged_skill_source` 查找来源；`skills.rs:1390` 的注册表查询按 name/id/后缀 `LIMIT 1`，缺少来源唯一性验证。找到来源后，`:1828` 备份原目录，替换后在 `:1837` 删除备份。该分支没有检查 `force` 或已修改文件。

触发场景：用户手工维护的技能与目录条目同名，或已修改的第三方技能被识别为可更新。普通更新即可走入此分支。扫描对此类目录没有受管 hash 基线，因此不能可靠标记 dirty。

影响：用户修改被整体替换；同名匹配可能选错上游。已有的受管技能 dirty 保护不能覆盖这个分支。

建议：默认只自动更新来源确定、具备基线的受管安装。对未受管目录显示“来源未确认”；接管必须展示来源并保留可恢复副本。没有基线时不得推断“未修改”。

验收：手工目录放入本地专属文件，普通更新拒绝覆盖；同名不同来源不能自动接管；接管或强制替换有明确可恢复记录。

### F03 目录同步失败仍报成功，内存目录与搜索数据库可能不一致

**证据：静态确定。** `src/services/skills/skill-catalog-service.ts:216` 直接把下载数组断言为 `CatalogSkill[]`；`:230` 吞掉 SQLite 写入失败，然后仍更新 lastSyncTime，并在 `:236` 返回 `success: true`。`src/stores/skill-explore.ts:450` 附近采用新内存目录，搜索却仍调用 SQLite。`src/components/skills/SkillsManagerModal.vue:260` 附近对服务返回的失败/缓存回退消息也统一使用 success toast。

触发场景：数据库写入失败，或远端数据只有 id/name 而缺少 UI 所需字段。后端只强制要求 id/name，对 tags/author/流水线成员等缺少完整契约检查。

影响：浏览到新条目，搜索到旧条目；重启丢失本次目录；下次自动重试被同步时间抑制。畸形条目还可能导致 `author.name`、`tags` 等访问异常。用户得到错误的成功反馈。

建议：远端 payload 在进入状态前做运行时校验；持久化成功后统一发布新目录版本。分别表达 downloaded、persisted、cached fallback 和 failed；失败返回值不能用成功 toast。

验收：模拟缓存写入失败，内存和 SQLite 保持上一完整版本，同步时间不推进；格式不合法的条目不能进入页面。

### F04 流水线和批量安装的结果存在“虚假完成”

**证据：执行复现。** `src/stores/skill-explore.ts:574` 用现有 catalog 过滤流水线 ID，缺失成员被静默丢弃；`:547` 和 `:603` 把所有 `res.success` 都计为新安装，忽略 `installedPaths: []` 的 skipped；部分失败分支也返回 `success: true` 并关闭向导。

隔离执行当前 store：流水线请求 `[repo-a, missing-skill]`，目录只有 repo-a，安装服务返回“已存在”、空路径。实际结果：`success:true, count:1, installedPaths:[], message:"成功安装 1 个技能"`。

影响：用户无法区分新装、已有、缺失和失败；没有逐项结果可重试。后端已有 partial/skipped 历史语义，前端安装总结果却退化成布尔值。

建议：先验证完整安装计划，再逐项输出 installed/skipped/failed/missing；批量结果提供 requested/completed/skipped/failed 计数和路径，部分失败保留明细与重试入口。

验收：缺少流水线成员时明确阻止或要求处理；全部已存在时新增数为 0；一半失败不能显示整套完成。

## P2：搜索、状态和可用性收敛

### F05 搜索在已有生产评测中未达标，CI 没有运行这个门槛

**证据：执行复现。** `src-tauri/tests/skill_search_poc.rs:2799` 调用生产 `search_skill_registry`。当前本机 3,176 条目录数据：黄金集 Strict P@1 为 26/26，盲测为 18/26（69.2%），Strict MRR@10 为 0.812。测试在 `:3521` 要求盲测 Strict P@1 ≥88%，本次断言失败。

`.github/workflows/ci.yml` 只运行 `cargo test --lib`，因此不会覆盖这个集成测试。目前测试文件还未跟踪，不能假设远端 CI 已包含它。

限制：这是测试内人工标注的小样本，本机目录数据和 debug 构建；不能据此断言所有查询准确率为 69.2%，也不能把 debug 延迟当成发布版性能。部分“盲测”标签在调参后会变成回归集，需要保留真正独立的留出集。

建议：整理固定的小型相关性基准进入 CI，覆盖中英文、混合查询、负例和多约束；生产评测中的错误结果先分类为数据问题、召回问题或排序问题，再决定是否调整词典。

### F06 类别筛选发生在搜索 Top-K 截断之后

**证据：静态确定。** `src/stores/skill-explore.ts:194` 传 `category:null`、`:197` 传 `limit:500`；类别实际由 `src/components/skills/explore/SkillExploreView.vue:346` 在收到结果后过滤。

影响：某类别中有匹配条目，但它排在全局第 501 名后时，类别筛选显示零结果；类别下拉和分页数量也只反映截断集合。“热门排序”也仅重排已召回集合，并非全目录热门结果。

建议：查询、stage、category、allowed IDs、排序、分页统一成同一个查询模型，先筛选后截断，返回明确 total/truncated 信息。不要仅增加 limit 掩盖问题。

验收：把目标类别唯一匹配技能放在全局第 501 名以后，类别搜索仍能找到。

### F07 自定义分类筛选逻辑错误，身份键也没有贯通

**证据：执行复现 + 静态确定。** `src/components/skills/installed/InstalledSkillsView.vue:450` 先按 agent/stage 筛选，再在 `:462` 判断自定义分类。选择 my-tag 时，先按 `agentType === 'my-tag'` 得到空集合。隔离执行此 computed：带 my-tag 的 Codex 技能结果数为 0。

另一个问题：已安装页面使用 `agent:folder` 的 `skill.id` 保存标签，目录详情使用 catalog ID 保存标签；`getCustomTags` 没有统一映射。按 Agent/阶段切换也保留旧 selectedFilter，可能留下在新维度不可见的过滤条件。

建议：筛选类型用明确联合类型，agent、stage、tag 是互斥分支；切换维度重置或转换过滤值。用户标签关联稳定 Skill identity，安装实例只是映射。

验收：给本地技能加标签后，两个页面能一致展示并筛选；从 Codex 切到阶段视图不会出现隐藏过滤条件。

### F08 “已安装”判断过宽，未区分来源、子技能和目标范围

**证据：执行复现。** `src/stores/skill-explore.ts:653` 的目录名/id/catalogId 匹配可提前返回 true，绕过来源校验；后续名称匹配也允许来源未知。隔离运行实际函数：相同 catalogId、不同 gitRemoteUrl，结果仍为 true。

即使身份匹配正确，当前判断也只是“任意扫描位置有实例”。在 Agent A 安装后，Agent B/项目 P 未安装时，目录页仍可禁用安装按钮。`AgentSkill` 也没有表达源 subPath 的字段，难以精确匹配同仓库多个单元。

建议：区分 Skill identity 与 Installation identity，来源未知时显示“可能匹配”，已安装状态展示具体目标，仍允许部署到其他目标。

验收：同名异源不互相覆盖；A 已安装不能阻止向 B/P 安装；父合集不等于所有子技能已安装。

### F09 默认排序不满足传递性，排序文案与实际规则不一致

**证据：执行复现。** `src/components/skills/explore/SkillExploreView.vue:384` 用“综合分差 ≥5 时按分数，否则按 stars”比较，导致循环比较。

使用实际比较器：A/B/C 的 halowakeScore 为 60/76/92，stars 都为 0，metrics.githubStars 为 100/10/1，得到 `compare(A,B)=-90`、`compare(B,C)=-9`、`compare(C,A)=-8`，即 A 在 B 前、B 在 C 前、C 又在 A 前。排序显示为热门，但实际还有认证、指南和评分加权。

建议：使用稳定的排序键或明确的分桶元组；热门按明确定义的热度，相关度使用唯一排序来源，不把阈值判断嵌入两两比较。

验收：比较器具备传递性，同集合不同输入排列得到一致结果；相同数据翻页/刷新不改变相对顺序。

### F10 更新检查把“不知道”表达成“没有更新”，批量失败反馈不足

**证据：静态确定。** `src-tauri/src/commands/skills.rs:1481` 后的检查循环忽略网络和 fetch 错误，仍返回普通技能列表；managed source 以整个仓库 HEAD 判断子技能更新。`remote_head_commit`、`quick_npm_view_version` 和共享 `run_git` 都没有代码级超时/取消。`src/components/skills/SkillsManagerModal.vue:249` 的批量更新只汇总 success，不显示失败明细。

影响：离线时可能提示全部最新；大仓库不相关提交使所有子技能提示更新；卡住的网络命令阻塞串行检查，关闭页面也不能取消；全失败时缺乏明确反馈。

建议：引入 up-to-date/update-available/unknown/error 状态，按来源合并请求、限制并发、设置超时并支持取消。对子技能明确区分“仓库有新提交”和“技能内容变化”。批量展示失败项与原因。

### F11 安装目标取自非响应式 localStorage，取消操作还可能改写偏好

**证据：静态确定。** `src/components/skills/explore/SkillInstallModal.vue:312` 的 computed 只读取 localStorage，没有响应式依赖；一旦求值，切换 Git 项目后它可能仍缓存旧路径。localPref 通过 `{...installPreference}` 浅复制，targetAgents 数组仍共享；添加 Agent 的 push 会在确认前改变 store 偏好。

影响：安装目标可能落到旧项目；取消向导不一定撤销选择。全局路径预览使用 catalog ID，而后端最终目录使用 SKILL.md 的 canonical name，路径提示也可能不准确。

建议：使用明确的响应式当前项目上下文，在打开向导时创建完整快照；复制数组；后端返回/预计算目标计划并在确认前展示真实目标路径。

验收：项目 A→B→打开安装向导，路径和最终安装位置都为 B；选择 Agent 后取消，偏好不变。

### F12 安装流程键盘可用性有明确缺口，复杂工作台仍嵌在可关闭模态框中

**证据：静态确定；视觉/实际焦点未运行。** `src/components/skills/SkillsManagerModal.vue:5` 关闭 focus trap；安装目标卡片使用点击 div，没有键盘语义；`src/components/skills/explore/SkillInstallModal.vue:975` 将合集/Agent checkbox `display:none`，无法获得原生键盘焦点。外层管理模态框始终 mask-closable/close-on-esc，未与安装状态同步约束。

影响：仅键盘用户不能完成所有安装选择；模态标识与焦点约束不一致。外层关闭时 IPC 可能仍执行，隐藏/卸载方式还需手动检查。

建议：优先恢复可操作的原生 radio/checkbox 和焦点管理；安装进行中外层与内层采用一致的关闭策略。后续把复杂 Skills 工作台迁入普通路由，顶栏按钮作为快捷入口；无需先扩大视觉改造范围。

### F13 更新与卸载使用不同的操作锁，前端扫描/更新状态也不统一

**证据：静态风险，未执行真实破坏性并发。** 更新使用 `acquire_skill_op_lock`，`src-tauri/src/commands/skills.rs:2719` 的卸载在路径校验后直接 remove_dir_all，不获取同一锁。前端 updatingPaths/uninstallingPaths 分开；scan 有世代号，checkUpdates 没有共享世代号。

影响：通过并发 IPC 发起卸载/更新时，校验、替换和删除可能交错；扫描和旧项目更新结果也可能覆盖新上下文列表。现有锁不能视为所有操作统一受保护。

建议：所有修改同一 installation 的操作采用同一锁；明确 project scope 与请求版本；扫描、检查、更新、卸载回写都校验当前 scope。

验收：在临时 fixture 上并发 update/uninstall，仅有一个操作获得执行权；A 项目检查晚返回不覆盖 B 项目当前列表。

## 全项目质量与其他模块

### F14 前端关键行为没有持续回归测试，CI 与发布链路覆盖不完整（P2）

优先加测试：合集多单元身份、来源未知时拒绝覆盖、partial/skipped/missing、缓存落库失败、筛选先于截断、当前项目切换和并发回写。无需先追求覆盖率百分比。

### F16 DevDock 启动去重不是原子的（P2，静态风险）

`src-tauri/src/commands/project_process/process_runtime.rs:369`（普通脚本）和 `:482`（配置命令）先 find_active_script，释放 processes 锁后才 spawn，之后插入记录。多线程并发调用可以同时通过检查。`list_processes` 按命令键只显示最新实例，这可能让重复进程更难发现。

建议在 project+command 键上先原子登记 starting，再启动进程，失败回滚。用临时小进程并发验证；本次未在真实项目执行重复启动。

### F17 日报加载没有请求版本保护（P2，静态风险）

`src/views/codex-report/CodexReportView.vue:260` 的 loadSessions 允许多个请求，返回后直接覆盖 sessions/includedIds；监听来源等变化也可触发加载。快速切换筛选时，旧请求晚返回可能覆盖新请求。

建议捕获查询快照并校验 request generation；与 Skills 请求版本保护采用一致模式。该模块主路径和本地解析已有实现，不应因这一风险判定整个日报不可用。

### F18 产品承诺、国际化与文档落后于实现（P2/P3）

`src/i18n/messages/zh-CN.ts:1194` 宣称“2900+ 经工程验证的端到端能力组合与流水线套餐”，但来源中包含未审查社区索引，执行评测也未达到现有门槛。badge 的“安全认证”仅由数据字段驱动；本次未发现应用内可核验的认证证据链，应表达清楚认证来源、范围和日期，不能把分数或仓库 stars 当作有效性保证。

Skills store 的失败/进度/成功消息及搜索命中摘要仍有中文硬编码；GitReviewPanel 的大量操作文案也硬编码中文。切英文后会混杂语言。

README 顶部仍为 1.2.3，实际版本为 1.4.1，功能矩阵尚未完整描述 Skills。版本、兼容矩阵、哪些目录仅扫描/哪些可以管理、浏览器预览与 Tauri 桌面能力应在同一处说明。

## 复杂度为什么失控

1. **产品角色扩张。** “查看并管理已安装 skills”逐渐成为“技能市场 + 推荐引擎 + 多工具包管理器 + 流水线平台”，每个角色都引入独立的数据和验收要求。
2. **身份没有唯一契约。** catalog ID、frontmatter name、folder name、agent:folder、gitUrl、subPath 在不同位置各自承担身份，兼容分支进一步稀释约束。
3. **结果模型跟不上批量操作。** 后端可以识别 skipped/partial，前端却以 success 布尔值和一条 message 结束流程，正确性被 toast 掩盖。
4. **多套状态和算法并行。** SQLite 搜索、内存目录、localStorage 标签、本地扫描、回退词典各自运行；缺少共同版本和上下文。
5. **修复成本被视觉复杂度放大。** 各页面已积累多层筛选、评分、徽章、视图模式与嵌套弹层，一个状态修改需要核对多个表达。
6. **验收集中在底层。** 118 项库测试是优势，但最容易使用户困惑的组合行为仍未进入持续测试；集成门槛也未接入 CI。

## 建议的收敛顺序

### 第一阶段：把安装管理做可靠

- 暂停新增流水线、评分维度、Agent 支持和自然语言排序启发式。
- 优先 F01/F02/F03/F04；统一身份、目标计划和逐项结果。
- 默认只自动更新本应用受管安装，其他来源先只读展示。
- 以真实目标路径为主反馈：来源、装到哪里、已存在/新安装/失败、能否安全更新/卸载。
- 完成最小前端回归集和安装边界 fixture 后，再开放合集批量能力。

退出条件：同仓库不同子技能不会误去重；用户文件不会被普通更新覆盖；任何“成功”都能对应真实结果；缓存与搜索同版本。

### 第二阶段：让搜索有可解释的契约

- 查询/过滤/排序/分页单一入口，过滤在 Top-K 前应用。
- 固定回归集、独立评测集和具体错误分类；避免看到一个搜索案例就补一条新同义词。
- 清楚区分精确匹配、通用退化、无结果、索引不可用和截断。
- 保留全文检索已有基础，决定哪些排序放后端；不要两端同时“优化相关度”。

退出条件：CI 能复现主类查询；类别不丢召回；排序稳定；失败和回退可辨认。

### 第三阶段：简化产品表面和职责

- 将已安装管理作为核心，探索作为次级入口；评分、套餐和自定义集合根据真实用途再决定保留程度。
- 若继续保留完整 Skills 工作台，迁为路由；只把安装确认留在弹层。
- 把本地技能详情与目录技能详情分开表达，避免把本地路径伪装成 gitUrl 后强制转为 CatalogSkill。
- 最后处理懒加载、组件样式重复、国际化和文档，不以视觉改版代替行为修复。

## 手动验证清单与预期结果

1. 首次启动、离线、有缓存三种状态：无目录/无网络/无搜索结果分别有明确提示。
2. 切换 Git 项目 A→B 后安装：展示和使用 B 的路径；不要求用户猜当前上下文。
3. 同合集两个子技能：两个目录都出现；再次执行提示已有，新增计数为 0。
4. 流水线缺成员或部分失败：展示逐项结果、保留失败项，并能重试。
5. 手工改动与异源同名：普通更新拒绝覆盖，来源显示明确。
6. 自定义标签、Agent/阶段切换、类别搜索：结果与筛选含义一致，没有不可见过滤条件。
7. 英文界面：安装、更新、搜索回退和审查文案不混入中文硬编码。
8. 仅用键盘：可以选目标/Agent/子技能；打开和关闭弹层的焦点合理；安装中外层关闭行为可预测。
9. 最小窗口 1120×720、系统缩放 125%/150%、长路径、长英文文本：关键按钮与反馈可见，内容可滚动。
10. 深浅主题、大量本地技能、连续搜索：检查可读性、列表稳定性和响应耗时。

## 后续开发的约束建议

每次 Skills 变更只围绕一个明确用例提交：先写触发条件、预期结果、身份和目标范围、失败状态及回归案例，再实现。优先用现有数据模型完成最小闭环。没有明确用户用例和验收标准的评分、推荐、兼容分支不继续添加。

推荐下一轮目标：**“选定一个来源确定的技能，安装到一个明确目标，成功可核验，失败可恢复，已安装状态准确。”** 这条链路稳定后，再讨论批量、推荐和流水线。
